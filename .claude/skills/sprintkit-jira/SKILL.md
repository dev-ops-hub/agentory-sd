# Jira and Confluence export

Mirrors a track's backlog into Jira Cloud and, when Confluence is configured, its planning documents into Confluence. This skill's own direction is one way, local → remote, and it is always what writes to Jira/Confluence: a dry run plus your approval, every time. Everything is written under `planning/` whether or not either is configured; Jira/Confluence are only contacted when configured and you approve a dry run.

The opposite direction — remote → local — is a separate, narrower mechanism: [.claude/sprintkit/JIRA-SYNC.md](../../sprintkit/JIRA-SYNC.md), run by `sprintkit-implement` and `sprintkit-autopilot` themselves before they build, not by this skill. When Jira/Confluence is configured, it becomes the source of truth for what it can represent (story title/description/status, dependency links, a sprint's spec content if its Confluence page exists) and gets pulled into the local markdown first; `**Touches:**` and the two whole-document pages (sprint plan, PRD/constitution) stay local-sourced regardless, for the reasons that file gives. When neither is configured, the markdown plan is the sole source of truth, exactly as before.

Formats for every file below: [references/comment-format.md](references/comment-format.md).

## Args

`track:<name>` (default track if omitted) and `scope:` a comma-separated list of `epics`, `stories`, `sprints`, `subtasks`, `speclinks`, `comments`, `docs`, `points`, `status`, `reports`, or `all` (default `all`). `speclinks` adds one web link from each story to its sprint spec (the Confluence page when one exists); `docs` publishes the planning documents to Confluence (step 5a); `comments` posts key decisions only (step 6). `points` pushes story-point estimates from the sprint file to Jira (step 5b). `status` transitions stories through the Jira workflow to match local status tracking (step 5c). `reports` publishes sprint review board reports (test, security, acceptance, clarifications) to Confluence (step 5d). `subtasks` is never added by a stage gate unless the user asks for it. A stage gate passes the scope it owns. `dry-run` stops after the dry run.

## Track and files

Default track: `planning/product-req-document(PRD).md`, `planning/sprint.md`, `planning/specs/sprint-<N>.md`. Named track `<name>`: `planning/<name>-product-req-document(PRD).md`, `planning/<name>-sprint.md`, `planning/specs/<name>-sprint-<N>.md`, and every output below is prefixed `<name>-`. Follow [.claude/sprintkit/SESSION.md](../../sprintkit/SESSION.md) (read the session file first, update it before stopping) and [.claude/sprintkit/CONSTITUTION.md](../../sprintkit/CONSTITUTION.md) (name `planning/constitution.md` with the constitution brief line in every agent brief).

## Configured or not

Read `agent-config/jira_confluence.json`, ignoring every key that starts with `_`. If it is missing but the old `agent-config/jira.json` exists, read that as the `jira` section and treat Confluence as not configured.

- **Jira is configured** only when `jira.enabled` is `true`, `site` and `jira.project-prefix` are non-empty, and `jira.board-id` is set whenever `sprints` is in `jira.levels`.
- **Confluence is configured** only when `confluence.enabled` is `true`, and `site` and `confluence.space-key` are non-empty.

Each is judged on its own. For one that is not configured: do not call it, say so in one line, and still run step 1. Do not look for the Atlassian MCP at all when neither is configured.

## Steps

1. **Build the outputs (always).** From the files above create `planning/scratchpad/` if it is missing and write `planning/scratchpad/jira-export.md` and `planning/scratchpad/jira-comments.md` there (working files: the export is regenerated every run, the comments file is an append-only decision log, never rewritten), and create `planning/scratchpad/jira-mapping.json` as empty if absent. The export is regenerated on every run from the PRD, the Sprint file and the specs; it is also the dry-run preview. Only levels listed in `jira.levels` and inside the requested `scope` are included. Never put chat text, prompts or secrets in any file.
2. **Stop here if neither is configured.** Report the file paths and that Jira and Confluence were skipped.
3. **Preflight.** Find the Atlassian MCP tools (ToolSearch for `atlassian jira`). If none are connected, stop with one line telling the user to connect the Atlassian MCP; the files from step 1 stay. Confirm the connected site equals `site`; for Jira, the project with key `jira.project-prefix` and the board exist; for Confluence, the space `confluence.space-key` exists. Check only what is configured. Any mismatch: stop and name it. Never fall back silently.
4. **Dry run.** Compare the export with `planning/scratchpad/jira-mapping.json` and show: items to create, update, skip, and comments to post, per level, and the Confluence pages to create, update or skip, plus the first few titles. State for every document link whether it will point at Confluence or the git host. Wait for approval (ask once); never write to Jira or Confluence without it, because what is sent may be cached or indexed. With `dry-run`, stop here.
5. **Create or update, in order:** Confluence pages first (step 5a), so the links below can use them, then epics, then stories (parent = epic key), then sprints (create on the board, assign their stories), then sub-tasks (parent = story key, only in scope when asked), then spec links, then dependency links ("is blocked by" from each sprint's `Dependencies:` line), then comments. Write the new key into `planning/scratchpad/jira-mapping.json` straight after each issue so a failed run resumes. Update an item already in the mapping instead of creating it again; never delete. An epic or story that left the plan is flagged in the report for the user to decide. After creating or updating a story or epic, also write the issue's returned `fields.updated` into `syncState.stories.<id>.updated` (or `syncState.epics.<id>.updated`) in the mapping — this is the baseline [.claude/sprintkit/JIRA-SYNC.md](../../sprintkit/JIRA-SYNC.md) compares against to detect a later Jira-side edit.
5a. **Confluence pages** (`docs`). Publish each document named in `confluence.documents` that exists, under the page titled `confluence.parent-page` (create it in the space if missing): `prd` the PRD, `constitution` `planning/constitution.md`, `sprint-plan` the Sprint file, `specs` every `planning/specs/*.md` (one page each), `sprint-graph` `planning/sprint-graph.md`, `retros` every file in `planning/retros/`, `ux` every file in `planning/ux/`, `adr` every ADR file. Page title = the document title, prefixed `<name>: ` for a named track. Convert the markdown to the Confluence format; render a `mermaid` block as a Confluence code block if no mermaid macro is available, never drop it. Put an info block at the top of each page with: **Created by** (the agent that wrote it), **Reviewed by** (the auditing agent, if any), **Approved by** (the person, with the date, from the document's own Status or Approved line) and **Source** (`<repo path>` at `<commit sha>`), then the line `Generated by sprintkit. Edit the markdown, not this page; it is overwritten on the next run.` Take the creator from the agent that produced the document, as recorded in `planning/session.md`, the document's own header or its Decisions entries in `planning/scratchpad/jira-comments.md`; when none of those names it, use the default for its type: `prd` and `constitution` `product-manager` (via `sprintkit-start`), `sprint-plan` `product-manager` (via `sprintkit-plan`), `specs` `technical-product-manager`, `ux` `ux-designer`, `adr` `solution-architect`, `sprint-graph` the `sprintkit-graph` skill, `retros` the `sprintkit-retro` skill. Reviewer defaults: `product-auditor` for the PRD and specs. Add the git author (`git log` of the file's first commit) as the human who committed it. If a name cannot be established, write `unknown`; never guess or invent one. Store page id and URL in the mapping under `confluence`, straight after each page, together with the page's returned `version.number` under `syncState.confluence.<doc>.version` — the baseline [.claude/sprintkit/JIRA-SYNC.md](../../sprintkit/JIRA-SYNC.md) compares against to detect a later direct edit on the page. Update a page already in the mapping (new version) instead of creating a second one; never delete a page, and flag a document that left the plan. Skip a page whose source is unchanged since the mapping's `sourceHash`. Use whichever Atlassian MCP operation creates or updates Confluence content (`discover` it if it is not a primary tool); if no operation can do it, stop and say so rather than skipping silently.

5b. **Story points** (`points`). Requires Jira and only runs when `points` is in scope. Read the Sprint file and find each story that has a `**Story Points:**` line and a mapped Jira key in the mapping's `stories`. For each, call `editJiraIssue` with `additional_fields: {"Story Points": <N>}` to set the story-point estimate on the Jira issue. Skip stories without a mapped key, without a points estimate, or whose mapped estimate already matches the Jira issue's current value. Report the count of issues updated and skipped.

5c. **Story status** (`status`). Requires Jira and only runs when `status` is in scope. Read the Sprint file and find each story whose acceptance criteria indicate completion status (all `[x]` = done, some `[ ]` with implementation started = in-progress, all `[ ]` and not started = todo). Map local status to Jira transitions:
   - `todo` → transition `11` ("To Do") — the default status, only transition if currently in a different status
   - `in-progress` → transition `21` ("In Progress")
   - `in-review` → transition `21` ("In Progress") — Jira has no dedicated "in review" status; use "In Progress"
   - `done` → transition `31` ("Done")
   For each mapped story, call `listJiraIssueTransitions` to find the available transition matching the target status, then call `transitionJiraIssue` with that transition ID. Skip stories whose Jira status already matches the target. Skip stories without a mapped key. Report the count of stories transitioned and skipped.

5d. **Review reports** (`reports`). Requires Confluence and only runs when `reports` is in scope. Read the report files under `agent-docs/review-reports/<track>/` for sprint `<N>`: `sprint-<N>-test-report.md`, `sprint-<N>-security-audit-report.md`, `sprint-<N>-acceptance-report.md`, `sprint-<N>-clarifications.md`. For each file that exists, create or update a Confluence page under the same parent page as `confluence.parent-page`, titled `Sprint <N> — <Report Type>` (e.g. "Sprint 1 — Test Report", "Sprint 1 — Security Audit Report", "Sprint 1 — Acceptance Report", "Sprint 1 — Clarifications"). Prefix with `<name>: ` for named tracks. Convert the markdown content to Confluence format with the same info block as step 5a (Created by `sprintkit-review`, Reviewed by the board member who produced it, Source pointing at the local file path and commit sha). Store the page id and URL in the mapping under `confluence.reports/sprint-<N>-test-report` etc. with `version.number` under `syncState.confluence.reports.<report>.version`. Update an existing page (by stable title) instead of creating a new one per iteration — the same sprint's reports are overwritten each review cycle. Skip when Confluence is not configured; do not attempt to publish reports as Jira artifacts. Report the count of reports published, updated, and skipped.

6. **Comments.** One comment per recorded decision, starting with its marker `[sprintkit:decision:<id>]` and built from the seven-section template in [references/comment-format.md](references/comment-format.md) (Context, Decision, Example, Why, Rejected, Impact, Dependencies), naming the agent and who decided it. If a recorded decision is missing a section, fill it from the PRD, spec or session file where the facts exist, otherwise write `None`; never invent facts. Append-only: a changed decision posts a new comment saying it supersedes the earlier one. Touch only comments that carry a marker; store comment IDs in the mapping. Post a decision once.
6a. **Key decisions only.** Post a recorded decision only when it is key: the user confirmed it, or it changes scope, safety behaviour (for example the confirmation rule, secrets, stale prices) or a cross-sprint interface (names, columns, signatures that another sprint builds on). Every other decision stays in `planning/scratchpad/jira-comments.md` with `Posted: not posted (not key)`. When a gate offers both, list the key ones in the dry run so the user can add or drop any.
6b. **Spec links** (`speclinks`). For each story whose sprint has an approved spec (its `**Spec:**` line is not `not written yet`), add one web link (`createJiraIssueRemoteIssueLink`) to the spec at a stable address. When Confluence is configured, `confluence.link-from-jira` is `true` and the spec has a page in the mapping, that is the Confluence page URL. Otherwise it is the GitLab or GitHub permalink at the commit that holds the approved spec (`<remote>/-/blob/<commit sha>/planning/specs/sprint-<N>.md`; `/blob/<sha>/...` on GitHub), and the git host is used only when no page exists; never mix the two for one story. Titled `Spec: Sprint <N> (approved <date>)`. Check the story's existing web links first (`listJiraIssueRemoteIssueLinks`): never add the same URL twice, because no operation removes a link. Store the URL in the mapping under `speclinks`. A later approved revision adds a new link titled with its date when the address is a git permalink; a Confluence page keeps one URL across versions, so no new link is added. A link already stored as a git permalink is not replaced when Confluence is enabled later; report it for the user.
7. **Report and save.** List what was created, updated, skipped and flagged, with Jira keys and Confluence page URLs. Add a History line to the session file.

## Rules

- Jira issue keys in branch names, commit prefixes and PR/MR titles are used by the other sprintkit skills only when `agent-config/git.json` exists and the mapping has a key; this skill only supplies the mapping.
- Priority mapping: P0 Highest, P1 High, P2 Medium. Labels: `sprintkit`, the plan ID (`EP-1`, `US-101`), the FR numbers, and `track-<name>` for named tracks. The plan-ID label lets the mapping be rebuilt if the file is lost.
- Rate limits: batch calls in groups of 20 with a short pause; the mapping makes any retry safe.
- A re-run with nothing changed creates nothing.
